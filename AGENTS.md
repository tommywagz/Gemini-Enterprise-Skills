# Gemini-Enterprise-Skills

Actual Agentic Solutions temporary development repository for the Gemini Enterprise Agent Skills Garden.

Build agent skills using the standard package architecture: a `SKILL.md` with a name, routing description, and actionable prompt, plus only the `scripts/`, `references/`, and `assets/` folders the skill needs. The [README.md](README.md) is the catalog and status record for skills already made.

## Skill to create: Black-Box Evaluation Suite Builder

**Proposed name:** `black-box-evaluation-suite-builder`

**Description:** Scaffold and implement executable black-box evaluation suites for software in the agent's current working directory. Trigger when a user asks for end-to-end, integration, acceptance, deployment, lifecycle, latency, compilation, or agent-capability evaluations. Inspect the repository's documented interfaces and runtime entry points, then build tests that verify observable behavior across deployment, normal use, failure and recovery, and shutdown. Do not trigger for a request limited to white-box unit tests or a review of an existing test report.

**Skill prompt and required behavior:**

1. Inspect the current directory before designing tests. Identify the software's components, supported features, public interfaces, deployment and startup paths, dependencies, configuration, build or compilation steps, health signals, and shutdown procedures from repository files and documented commands. Record assumptions and identify components that cannot be exercised in the available environment. Use behavior visible at public boundaries as the test oracle; do not make private implementation details the basis of success.
2. Produce a coverage matrix linking each applicable component and feature to deployment, use, failure or recovery, and shutdown cases. Include positive, negative, malformed-input, permission, dependency-failure, and repeated-run cases where relevant. Make fixtures isolated, cleanup repeatable, and assertions specific enough to distinguish a product failure from a broken test environment.
3. Design functional cases using the [ISTQB Foundation Level Syllabus](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) and the [ISO/IEC/IEEE 29119 software testing series](https://standards.ieee.org/wp-content/uploads/import/documents/tocs/ISO_IEC_IEEE_29119.pdf):
   - **Equivalence partitioning:** define valid and invalid input classes, then choose representative cases for each class rather than redundant examples.
   - **Boundary value analysis:** exercise values at, just below, and just above documented limits, including empty and maximum-size values where meaningful.
   - **Decision tables:** enumerate relevant condition combinations and expected outcomes for multi-rule behavior; prune impossible combinations explicitly.
   - **State transitions:** define permitted states and events, then test valid transitions, rejected transitions, recovery, and terminal states.
4. Add empirical performance cases where the product exposes measurable build, compilation, request, or data-transfer behavior. Follow [SPEC's reproducibility and reporting principles](https://www.spec.org/cpu2017/Docs/runrules.html): document hardware, software versions, configuration, workload, warm-up, sample count, and measurement method; run repeated trials under controlled conditions. Report median and P90/P99/P99.99 latency when sample sizes support those percentiles, with explicit percentile calculation and raw samples. Measure payload scaling over increasing byte sizes and record throughput and latency. For packet or event streams, define the interarrival or delay-variation measure used for jitter and report average and maximum jitter. Set pass thresholds from project requirements or a recorded baseline, never invented universal limits. Measure clean and incremental compilation separately when applicable. Label any small-sample tail estimate as inconclusive.
5. If the software includes an AI agent, add outcome-based capability and usability scenarios inspired by [SWE-bench](https://arxiv.org/abs/2310.06770) for real issue resolution and executable verification; [GAIA](https://arxiv.org/abs/2311.12983) for multi-step reasoning and multimodal tool use; [AgentBench](https://arxiv.org/abs/2308.03688) for constrained, multi-turn environments; [WebArena](https://arxiv.org/abs/2307.13854) for final-state UI success; [ToolBench](https://arxiv.org/abs/2307.16789) for API discovery and use; and [MINT](https://arxiv.org/abs/2309.10691) for recovery after tool errors or natural-language feedback. Adapt scenario length and complexity to the product. Evaluate observable task completion, valid tool actions, recovery, and user-facing clarity rather than a prescribed action path. Use local fixtures or approved sandbox services so scenarios are reproducible.
6. Implement the suite in the repository's existing test framework when practical. Provide runnable commands, fixtures, test data, expected outcomes, environment prerequisites, cleanup, and a report that distinguishes pass, fail, skipped, and inconclusive results. Trace each test back to the coverage matrix and explain any untested component or feature.

**Expected package:** `SKILL.md` for the workflow and routing description; `references/` for source links, test-design examples, benchmark methodology, and report schemas; optional `scripts/` for deterministic suite scaffolding or measurement helpers. Include only folders with actual content.
